# utest / sprint quirks encontrados no sprint 007 (feature 4.3)

Escrito para virar issue(s) no `~/utest` e no `~/sprint-cli`. Cada item: o sintoma, a
repro mínima, o diagnóstico (quando cheguei nele), e o impacto no fluxo de quem usa.

Ambiente: `~/tui`, Bun 1.3.12, `../utest/utest.js` como runner (`.sprint/config.json` →
`"test": "../utest/utest.js ."`).

---

## 1. Rodar UM arquivo `.t.js` alvo não imprime resultado — ✅ RESOLVIDO (utest sprint 017)

**Sintoma:** `bun ../utest/utest.js plugins/eval/super-sink.t.js` (ou qualquer `.t.js` por
caminho) imprime só:

```
coverage: —
```

e sai com código 0 — sem lista de testes, sem contagem, sem falha. Vale pra QUALQUER
arquivo, não só um novo (confirmado com `plugins/eval/pty.t.js`, que tem 34 testes
saudáveis). Com `-v:2` / `-v:3` o comportamento não muda.

**Repro:**
```
cd ~/tui
bun ../utest/utest.js plugins/eval/pty.t.js          # → só "coverage: —", exit 0
bun ../utest/utest.js .                              # → roda tudo, relatório completo
```

**Diagnóstico parcial:** o arquivo É executado (o sidecar `.utest/<mangled>.json` é escrito
com `tests`/`checks`/`failCount` corretos), mas o RELATÓRIO some. Suspeita: o caminho
`_isFile` em `runPhase` (utest.js ~460) monta a entry, mas o render do relatório de fase é
pulado quando `entries.length === 1` e não é fase `unit`, OU o `belongs` glob-match
(`inc.some(g => new RegExp(...).test(...))`) falha pra esse arquivo e ele cai numa fase
vazia. A saída `coverage: —` é a de uma fase sem entries.

**Workaround atual:** sempre `bun ../utest/utest.js .` (a suíte inteira, ~15–30s) e ler o
veredito de um arquivo específico no sidecar `.utest/`. Para iterar rápido num arquivo só,
não há caminho — o que dói em TDD.

**Impacto:** alto para desenvolvimento. O ciclo "escrevo teste → rodo só ele → vejo
vermelho → corrijo" não funciona; cada iteração custa a suíte inteira.

**Correção (utest sprint 017, feature 3.2):** o `belongs` do ramo `_isFile` em `runPhase`
era um regex glob montado à mão — trocava `**/`→`(.*/)?` e DEPOIS `*`→`[^/]*` sobre a
string toda, corrompendo o `.` interno de `(.*/)?` para `(.[^/]*/)?`, que casa exatamente
UM nível de pasta. Agora usa `scanner.js#makeFilter` (o mesmo `compileGlob` do walk:
fast-path + minimatch). Junto: `rawTarget` passou a ser absolutizado ANTES do
`process.chdir(root)` — um alvo relativo resolvido depois do chdir (para a pasta do próprio
alvo) duplicava o caminho. Coberto em `scanner.t.js` §"makeFilter".

## 2. A linha-resumo `📄N 🧪M ✔K` às vezes não reflete um arquivo novo

**Sintoma:** ao adicionar `plugins/eval/super-sink.t.js` e rodar `bun ../utest/utest.js .`,
a linha final continuou `📄25 🧪196 ✔512` — a mesma de antes do arquivo existir. O sidecar
`.utest/plugins__eval__super-sink.t.js.json` porém tinha `{tests:8, checks:19, failCount:0}`
— o arquivo rodou.

**Como desconfundir:** `git stash` (tira as mudanças) → `utest .` → anota o baseline
(`📄24 🧪188 ✔493`); `git stash pop` → `utest .` → compara (`📄25 🧪196 ✔512`). O delta
(+1 arquivo, +8 testes, +19 checks) confirmou que o arquivo ESTAVA sendo contado — a linha
que eu tinha lido antes era de uma rodada com cache parcial / estado sujo.

**Diagnóstico:** provável interação com o cache (`results.json` + o cache-ledger do iodb).
Uma rodada logo após mexer em `.utest/` (ver item 4) ou após um `--force` interrompido
deixa a contagem estável no valor antigo até o próximo `.` completo e limpo.

**Impacto:** médio. Leva a concluir "meu teste não é pego" quando ele é. `--force` +
baseline por `git stash` é o jeito confiável de medir.

## 3. Fase com provider (`eval`, `tty`) não roda sob `utest .` — ✅ RESOLVIDO (utest sprint 017)

**Sintoma:** `bun ../utest/utest.js .` roda só a fase `UNIT`. Para rodar a fase `eval` ou a
`tty` é preciso nomeá-la: `bun ../utest/utest.js eval`, `bun ../utest/utest.js tty`.

**Repro:**
```
bun ../utest/utest.js .        # → UNIT só
bun ../utest/utest.js eval     # → EVAL (34 testes)
bun ../utest/utest.js tty      # → TTY
```

**Diagnóstico:** `phaseNames = Object.keys(cfgRaw).filter(k => !RESERVED && (cfgRaw[k]?.include || entriesFor(k)))`
(utest.js ~396). Uma fase provider (sem `include:` no YAML) só entra em `phaseNames` se
`entriesFor(k)` já está registrado — o que depende do módulo `boot:` ter rodado. Mesmo
registrado, o comportamento observado é que `.` roda só `unit` e as demais são alvo
explícito. Pode ser intencional (fases caras = opt-in), mas não está documentado e é uma
armadilha para CI.

**Impacto no `sprint close` / CI:** o "critério de pronto" `utest .` verde é INCOMPLETO —
não exercita `eval` nem `tty`. O CI (e o humano no `close`) precisa rodar os TRÊS:
`utest .` **E** `utest eval` **E** `utest tty`. Vale o `sprint` gerar isso, ou o
`.sprint/config.json` aceitar uma lista de comandos de teste.

**Diagnóstico real (não era decisão de design):** um `.t.js` da fase `unit` —
`plugins/eval/utest-phase.t.js` L17-20 — chama `registerEvalPhase({ entries: async () => [] })`
e POLUI o singleton `ENTRY_PROVIDERS` de `kinds.js`. Nas fases seguintes do mesmo processo,
`entriesFor('eval')` devolve esse provider-fixture vazio → `runPhase('eval')` produz 0
entries → EVAL some do relatório. `utest eval` sozinho funciona porque `unit` nunca roda e
o provider fica `null` (cai no `scan()` glob). Mesma classe do item #4.

**Correção (utest sprint 017, feature 3.4):** `kinds.js` ganhou `resetRegistry()` (zera
`ENTRY_PROVIDERS`/`EXECUTORS`/`PHASE_SETUPS`, restaura `KINDS` ao vocabulário do import).
`utest.js` extraiu o loop `boot:` para `runBoot()` e, entre CADA par de fases, chama
`resetRegistry()` + `runBoot()` — cada fase parte do registry que só o `boot:` monta, não
do que os `.t.js` da `unit` deixaram. Verificado: `utest .` agora mostra UNIT + EVAL (11
📄 / 44 🧪) + TTY, a mesma contagem de `utest eval`. Coberto em `kinds.t.js` §"resetRegistry".

**Ainda pendente (não neste sprint):** (a) `utest .` sai com exit 0 mesmo com `EVAL ✘1` —
o exit code não agrega as fases provider (relacionado ao item 5); (b) o `.t.js` do `~/tui`
deveria restaurar o registry no `finally` (helper `withRegistry`) em vez de depender da
rede do utest — o `resetRegistry` é a rede, não a licença pra poluir.

## 4. `configure()` do plugin eval é estado global — um `.t.js` polui o outro

**Sintoma:** rodar `utest .` (fase unit) e logo em seguida `utest tty` no MESMO processo →
`💥 ENOENT: no such file or directory, open '/tmp/eval-script-t-XXXX/1.1.eval.js'` na fase
`tty`. O `1.1.eval.js` num tmpdir é fixture de OUTRO teste (`plugins/eval/script.t.js` /
`utest-phase.t.js`), que faz `configure({ scriptPathFor: () => <fixture> })` e nunca
restaura.

**Repro:**
```
bun ../utest/utest.js .        # fase unit: script.t.js chama configure({scriptPathFor})
# ...a mesma invocação continua pra fase tty:
                               # tty executor → sweepFeature → loadEvalScript → cfg.scriptPathFor
                               #   → ainda aponta pro tmpdir do script.t.js → ENOENT
```

**Diagnóstico:** `plugins/eval/config.js` guarda `scriptPathFor`/`expand`/`seed`/`renderFor`
num objeto `state` de módulo. `configure(opts)` faz merge e não há `resetConfig()`. Qualquer
teste que chama `configure(...)` altera o global para todos os testes seguintes na mesma
rodada — e as fases rodam em sequência no mesmo processo.

**Workaround aplicado no 4.3:** `tty-phase.js#registerPhaseSetup` chama
`configure({ scriptPathFor: zssScriptPathFor })` no início da fase, restaurando o default.
Frágil — o próximo campo poluído (`expand`, `seed`) repete o problema.

**Sugestão:** `configure()` retornar um `restore()`, ou o utest chamar um `resetConfig()`
por fase entre `phaseSetup`s, ou os testes que mexem em config usarem um helper
`withConfig(opts, fn)` que restaura no finally.

**Impacto:** alto e silencioso. Só apareceu porque a fase `tty` roda DEPOIS da `unit` no
mesmo processo. Qualquer fase nova que dependa do `cfg` do eval vai bater nisto.

## 5. Sidecar de cache com `failed:true` de outra data não expira sozinho

**Sintoma:** `.utest/plans__1-runtime__1.2.eval.js.json` com `{"failed":true, "seen":0,
"mtime":<data antiga>}` persiste entre rodadas. `grep -l '"failed":true' .utest/*.json`
sempre acha ele, mesmo quando `utest .` sai verde (porque `.` não roda a fase `eval`, item
3). Confunde: parece regressão nossa, é resíduo.

**Diagnóstico:** o sidecar é escrito pela fase `eval`; `utest .` não roda essa fase, então
nunca o revalida nem o apaga. `1.2.eval.js` de fato falha em `utest eval` (`✘1` — parece
pré-existente, não introduzido pelo 4.3).

**Impacto:** baixo, mas atrapalha o "está tudo verde?" — o sinal confiável é o EXIT code de
CADA fase nomeada, não a varredura dos sidecars.

## 6. `.utest/results.json` é índice — apagá-lo quebra `utest <termo>` até o próximo `.`

**Sintoma:** apaguei `.utest/results.json` tentando forçar re-scan. Depois disso,
`bun ../utest/utest.js super-sink` (filtro por termo, não path) não resolvia mais para o
arquivo — o mecanismo "termo → chave de results.json → rawTarget" (utest.js ~285) tem zero
entradas e cai em filtro de nome, que não casa nada até uma rodada `.` completa reconstruir
o índice.

**Impacto:** baixo, mas é uma pegadinha: `results.json` parece um cache descartável e é
semi-índice. Documentar "não apague à mão; use `--force`".
