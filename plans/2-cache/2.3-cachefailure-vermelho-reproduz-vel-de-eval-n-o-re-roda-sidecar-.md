# [2.3] cacheFailure — o vermelho que não re-roda

Um `.t.js` vermelho é barato de re-rodar.

## Objetivo

Um `.t.js` vermelho é barato de re-rodar. Um passo de eval que gasta 10s subindo Chromium
só para reconfirmar o mesmo vermelho é desperdício puro. Quem chama `write` com
`{ cacheFailure: true }` grava o resultado vermelho num sidecar; `read` o reusa enquanto
o carimbo e as deps baterem.

## Estado atual — 🟡 testada

`cache.t.js` §"falha REPRODUZÍVEL não re-roda" (6 testes): sem marca busta, com marca
reusa com `failed:true`, alvo reeditado invalida, dep mexida invalida, passar limpa o
sidecar, `extraDeps` governam. Verde 2026-09-03.

## Accomplishments

- Fecha o critério de aceite do `sprint eval --sweep` do soml: fase `eval` inteira,
  vermelhos incluídos, cai de dezenas de segundos para um `stat` por arquivo.
- Restrição de segurança preservada: `cacheFailure` **nunca** para um passo `real`/`linear`
  (que roda contra o projeto vivo) — só sandbox 100% reproduzível.
- Sprint 007: o sidecar (`selfFile`) foi de `.bot/.utest/` (nome legado de `~/bot`) para
  `.utest/`, a mesma pasta do `results.json` — um diretório de cache só no repo.

## Debts

- A decisão de "é reproduzível" mora no chamador (`apps/eval/utest-phase.js` no soml), não
  aqui — o utest confia na marca. Um chamador errado cacheia um falso vermelho.
- Sem `.eval.js` (`2.3.eval.js`).
