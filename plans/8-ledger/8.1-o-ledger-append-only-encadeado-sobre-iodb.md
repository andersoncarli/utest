# [8.1] o ledger append-only encadeado sobre iodb

Ver o `_front.md` desta frente para a tese, a linhagem (`~/bot/cmds/testio`) e quem consome.
Esta feature entrega o ledger em si.

## O que ler antes de escrever uma linha

Nesta ordem, e sao poucos arquivos:

1. `~/bot/cmds/testio/audit.js` — **72 linhas**. E o alvo a assimilar, quase literalmente.
   `openAudit` faz o que `openLedger` tem que fazer; a diferenca e que aquele grava em
   `.bot/testio-runs` e este grava em `.utest/ledger`.
2. `~/iodb/io-engine.js` — a API: `IO(path, { reduce, initial, type, entity })`, e o objeto
   devolvido (`open`, `in`, `flush`, `get`, `out`, `records`, `verify`, `header`, `state`).
   `append` e o `reduce` a usar (`export const append` no fim do arquivo).
3. `~/iodb/hash.js` — so para ENTENDER, nao para copiar: `sha64`, `canonical`, `makeFullKey`,
   `verify`. A formula e `key = sha64(payload) XOR sha64(prevKey)`; `'0'` e `'1'` sao aliases
   reservados (genesis e projecao).
4. `~/bot/cmds/testio/ARCHITECTURE.md`, secao "Pipeline Alvo" → **4. Record** — a lista de
   eventos e a doutrina.

## A forma do modulo

```js
// ledger.js
import { readFileSync } from 'fs'
import { join, relative } from 'path'
import { createHash } from 'crypto'
import IO, { append } from '../iodb/io-engine.js'

const sha256 = (file) => {
  try { return createHash('sha256').update(readFileSync(file)).digest('hex') }
  catch { return null }
}

export function openLedger(root, options = {}) {
  const runId = `${new Date().toISOString()}-${Math.random().toString(36).slice(2, 8)}`
  const io = IO(join(root, '.utest', 'ledger'), {
    reduce: append, initial: [], type: 'test-run', entity: 'utest',
  })
  io.open({ _entity: 'utest', _type: 'test-run-log' })

  const write = (event, payload = {}) =>
    io.in({ event, runId, at: new Date().toISOString(), ...payload })

  return {
    runId, write,
    start(files) { /* run:start com fileSet+sha256, phase, target, total */ },
    test(file, result) { /* test:result */ },
    event(workerEvent, payload) { /* worker:<event> */ },
    end(summary) { write('run:end', summary); io.close() },
    verify: () => io.verify(),
    out: (h) => io.out(h),
  }
}
```

A degradacao (requisito "custo zero quando desligado") e um `try/catch` no import dinamico do
`iodb` devolvendo um objeto com a MESMA forma e todos os metodos no-op — `verify()` devolve
`{ valid: true, length: 0 }`. Quem chama nunca testa se o ledger existe.

## Onde plugar no `utest.js`

Tres pontos, e so tres:

- **abertura** — onde a fase comeca e o conjunto de arquivos ja esta resolvido: `openLedger`
  + `start(files)`.
- **por teste** — no mesmo lugar onde hoje `results.record(...)` e chamado (`cache.js` linha
  ~554, *"`results.record` roda SEMPRE, verde ou vermelho"*): `ledger.test(file, result)`.
- **fim da fase** — onde hoje `results.flush()` e chamado incondicionalmente:
  `ledger.end(summary)`.

Nao inventar um quarto ponto. Se um evento nao cabe nesses tres, ele provavelmente pertence a
outra feature.

## O que NAO fazer nesta feature

- **Nao mexer no cache.** `results.json` e a regra do mtime sao da frente 2 e continuam como
  estao. O ledger nao le o cache e o cache nao le o ledger.
- **Nao reimplementar hash/encadeamento.** Isso e do `iodb`. Se algo falta la, e feature do
  `iodb`, nao daqui — reportar, nao consertar.
- **Nao derivar estatistica de garantia** (o "validada N vezes em M dias") — isso e consumo,
  e mora no `~/tui` 3.2 e no `sprint`. Esta feature so PRODUZ o log.
- **Nao dar semantica ao evento de plugin.** O `utest` aceita, encadeia, persiste. Ponto.
- **Nao trazer o resto do `testio`** (worker, discover, render). So o `audit.js`.
